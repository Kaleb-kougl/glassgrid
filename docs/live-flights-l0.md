# Live flights L0: spike and fixture

Branch `live-flights`, dated 2026-11-10. Milestone L0 of the live-flights
feature: real air traffic over the San Francisco Bay Area as data
Glassgrid can open, from [adsb.lol](https://adsb.lol) (ODbL 1.0). It builds
the shared point schema, a pinned one-day fixture from adsb.lol's
whole-sky archive, and a recorder for its live API. Nothing in the app
uses it yet.

| Goal | Result |
| --- | --- |
| One schema for live and archive fixes | `FlightPointSchema` (Zod) in `packages/core/src/flights`, with pure adapters `fromReadsbAircraft` (live / aircraft.json objects) and `fromTracePoint` / `fromTrace` (archive trace files), the Bay Area box and `inBbox`. The adapters never throw and return `null` for unusable input (property-tested). |
| A pinned fixture from the archive | `globe-history` streamed `v2026.11.09-planes-readsb-prod-0` (two parts, 3,723,313,664 bytes) through a streaming tar reader without writing it to disk: **1,456,777 fixes of 2,379 aircraft** in the box that UTC day. Day file **14.5 MB**, 30-minute window **0.76 MB**, both zstd Parquet, committed with a manifest and an ODbL notice. |
| Aircraft in view | Per 10 s snapshot over the day: **peak 183, median 79** (mean 82.8). Busiest 30 minutes: 23:28–23:58 UTC (15:28–15:58 PST), 382 distinct aircraft, 169 in view at the median snapshot. |
| Reproducible | Two independent runs (one fresh download each) gave the same asset SHA-256s and byte-identical Parquet files. |
| Live recorder | `record-flights` polls adsb.lol every 10 s, dedups on (hex, ts), backs off on 429 / 5xx, writes the same layout with `source = 'live'`. Tested with a mocked `fetch` and fake timers only: **api.adsb.lol is not reachable from the build environment**, so the endpoint is unverified (below). |
| Attribution | `apps/web/public/samples/flights/LICENSE-ODbL.md`, the manifest's `licence` block, a row in `THIRD_PARTY_NOTICES.md` (generated by `scripts/third-party-notices.js`, `--check` passes). |

## The data

### Formats, as verified

The formats come from readsb's
[README-json.md](https://github.com/wiedehopf/readsb/blob/dev/README-json.md)
("aircraft.json" and "trace jsons"). The archive was checked against the
real release:

- **The release** is one GNU tar split into `<tag>.tar.aa` (2,000,000,000
  bytes) and `<tag>.tar.ab` (1,723,313,664). Paths start with `./`. It
  begins with `heatmap/*.bin.ttf` (several hundred MB), then 71,773
  `traces/<xx>/trace_full_<hex>.json` files (gzip despite the name), then
  `acas/`, `README.txt`, `LICENSE-ODbL.txt` and `LICENSE-cc0.txt`.
- **A trace file** is `{ icao, r, t, dbFlags, desc, version, timestamp,
  trace }` with `timestamp` at 00:00 UTC of the day (1794182400). Every point
  in this release has the 14 elements the README lists:
  `[secondsAfterTimestamp, lat, lon, altitude ft | "ground" | null, gs kt,
  track deg, flags, verticalRate fpm, aircraftObject | null, positionType,
  geomAltitude, geomRate, ias, roll]`. The aircraft object (callsign,
  squawk, category, ...) appears on some points only.
- **The GitHub releases API** was not reachable from the build environment
  (403 for this repository), so the tool found the parts by probing
  `.tar.aa`, `.tar.ab`, `.tar.ac` with one-byte Range requests until the 404.
  It tries the API first; with the API, the manifest would also carry
  GitHub's own asset digests (`githubDigest`, null here).

### Mapping to `FlightPoint`

| Field | Live (`fromReadsbAircraft`) | Archive (`fromTracePoint`) |
| --- | --- | --- |
| `ts` (epoch ms, integer) | `round((now - seen_pos) * 1000)`, falling back to `seen`, then `now` | `round((timestamp + point[0]) * 1000)` |
| `hex` | `hex`, lowercased; `~` prefix (non-ICAO) kept | `icao` |
| `flight`, `squawk`, `category` | the object's fields (callsign trimmed) | this point's aircraft object, else carried forward from the last one; reset on a new leg (flag 2) |
| `registration`, `typeCode` | `r`, `t` | the file's `r`, `t` |
| `lat`, `lon` | `lat`, `lon` only (`lastPosition`, `rr_lat` ignored) | `point[1]`, `point[2]` |
| `altBaroFt`, `onGround` | `alt_baro`; `"ground"` → onGround, null altitude | `point[3]`; same; null when flag 8 says the altitude is geometric |
| `altGeomFt` | `alt_geom` | `point[10]`, else `point[3]` under flag 8 |
| `gsKt`, `trackDeg` | `gs`, `track` (on the ground: `true_heading` if no track) | `point[4]`, `point[5]` (true heading on the ground, per the README) |
| `baroRateFpm`, `geomRateFpm` | `baro_rate`, `geom_rate` | `point[7]` (geometric under flag 4), `point[11]` |
| `posType` | `type` | `point[9]` |
| `source` | `'live'` | `'archive'` |

Malformed optional fields become `null` one by one; only a missing or
invalid hex, time or position drops the point. Every result is checked
with `FlightPointSchema`.

### Parquet layout

`FlightPoint`'s fields in `FLIGHT_POINT_FIELDS` order and names. `ts` is a
UTC timestamp with millisecond precision (Parquet `TIMESTAMP(MILLIS)`,
DuckDB reads it as `TIMESTAMP`), `lat` / `lon` are `DECIMAL(7,5)` /
`DECIMAL(8,5)` (about 1 m), altitudes and rates `INTEGER`, speed and track
`DOUBLE` to 0.1. Rows are sorted by (hex, ts); a replay reads them with
`ORDER BY ts`. zstd level 19, row groups of 122,880, Parquet v2 encodings,
one writer thread.

The first cut, sorted by time with `DOUBLE` positions, made a 34.0 MB day
file, over the 20 MB target. Measured on the same 1,456,777 rows:

| Change | Day file |
| --- | ---: |
| sorted by (ts, hex), `DOUBLE` lat/lon, µs timestamps | 34.0 MB |
| sorted by (hex, ts) | 24.7 MB |
| ... and `DECIMAL` lat/lon (delta-encoded integers instead of byte-stream-split doubles) | 15.4 MB |
| ... and millisecond timestamps (**used**) | **14.5 MB** |
| ... and `DECIMAL` speed and track | no gain |

So no point and no column was dropped to fit.

## Numbers

From `flights.manifest.json` and the run logs. 2-core VM, Node 22.23, DuckDB 1.5.6.

| Measured | Value |
| --- | ---: |
| Release streamed | 3,723,313,664 bytes in 167 s (22.4 MB/s); whole run 179 s. The verification run: 247 s at 15.1 MB/s |
| Trace files read | 71,773 (none unreadable) |
| Aircraft with a fix in the box | **2,379** |
| Fixes in the box | 1,463,749; 6,972 repeated an aircraft's timestamp (two positions a few metres apart; 81% of those fixes are ADS-R, 16% TIS-B) and were dropped: **1,456,777 rows** |
| Aircraft in view per 10 s snapshot, whole day (8,640 snapshots) | **peak 183** at 23:27:30 UTC (15:27:30 PST), **median 79**, mean 82.8 |
| Busiest 30 minutes | 23:28–23:58 UTC: 382 distinct aircraft; in view peak 182, median 169 |
| `flights-bay-day.parquet` | 14,471,875 bytes, SHA-256 `a7274a7b…8b30` |
| `flights-bay-30min.parquet` | 758,942 bytes, 71,595 rows (with the 60 s lead-in), SHA-256 `06aac9fd…f2ac` |
| Cadence | median 2.1 s between an aircraft's fixes, p90 10.4 s |
| Field coverage | on the ground 35.4% of fixes; callsign 98.2%; squawk 92.5%; category 98.3%; registration 97.5%; barometric altitude 64.5% (the rest are on the ground or geometric only) |
| Sources | `adsb_icao` 86.0%, `adsr_icao` 12.7%, TIS-B 0.9%, MLAT 0.2%; 12,042 fixes have a non-ICAO (`~`) address |

**Aircraft in view** is the snapshot a 10 s live poll would show: at each
tick, every aircraft whose latest in-box fix is under 60 s old. Fixes
outside the box are not kept, so an aircraft that leaves stays "in view"
for up to 60 s after its last fix inside. **Busiest window**: windows start
on whole minutes; the score is distinct aircraft in the window's
snapshots, ties broken by total aircraft-snapshots, then the earliest start.

  (both asset names, sizes and SHA-256), the filters and roundings applied,

## Unverified

- **The live endpoint.** `adsbLolPointUrl` builds
  `https://api.adsb.lol/v2/point/{lat}/{lon}/{radius_nm}` from adsb.lol's
  "drop-in replacement for the ADSBExchange v2 API" claim. It has not been
  checked against the Swagger page (https://api.adsb.lol/docs), which the
  proxy blocks. To check, from a network that allows it: the path, the
  radius cap (assumed 250 nm; the Bay Area query is 58 nm), and whether
  responses are `{ ac, now, total, ... }`.
- **Live field units.** Assumed to be readsb's: `now` in milliseconds
  (the `&jv2` format; `readsbNowSeconds` also accepts seconds),
  `seen_pos` in seconds, `alt_baro` in feet or `"ground"`, `gs` in knots,
  rates in ft/min. `record-flights --raw FILE` saves every response for
  this check.
- **Rate limits.** Unknown. The recorder makes one request per 10 s and
  honours `Retry-After`.
- **GitHub's digests** of the release assets were not compared (no API
  access); the SHA-256s in the manifest are computed while streaming, and
  matched across two downloads.

## Caveats

- **The day is a UTC day**: 16:00 PST on 8 November to 16:00 PST on 9
  November. The busiest window (15:28–15:58 PST) sits at its end; the
  Bay Area's evening peak continues into the next UTC day, which this
  fixture does not include.
- **The fixtures are served as public web files.** `/samples/*.parquet` is
  cached as immutable (`apps/web/vercel.json`), so a different day needs new
  file names. The release tarball (`pnpm package:web`) now carries the
  15.2 MB folder too.
- **One instance.** `prod-0` is one of adsb.lol's readsb instances; whether
  other instances hold different coverage for the same day was not checked.

## Reproduce

```sh
# Streams about 3.7 GB from GitHub (about 3 minutes at 22 MB/s); writes apps/web/public/samples/flights/
NODE_USE_ENV_PROXY=1 pnpm --filter @glassgrid/datasets globe-history -- --date 2026-11-09 --release prod-0
# Redo the outputs from the extracted fixes kept in tools/datasets/out/cache/flights/ (no download)
pnpm --filter @glassgrid/datasets globe-history -- --date 2026-11-09 --reuse-cache
# Live (needs api.adsb.lol)
NODE_USE_ENV_PROXY=1 pnpm --filter @glassgrid/datasets record-flights -- --minutes 30 --raw tools/datasets/out/flights/raw.ndjson
pnpm --filter @glassgrid/datasets test
pnpm --filter @glassgrid/core test
```
